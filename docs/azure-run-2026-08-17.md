## Read this first: what counts as real

**5,271 events are in the database. 3,714 of them are genuine internet traffic.**

The difference is this project's own traffic generator. `attacker/run.py` was run
against the sensor from a residential connection, and because it arrived over
the real internet it received real geolocation — Philippines, ComClark Network &
Technology Corp — making it indistinguishable from a genuine attacker in every
view. It is identifiable only by its payloads matching
[`attacker/scenarios/iot_botnet_mimic.yaml`](../attacker/scenarios/iot_botnet_mimic.yaml)
verbatim, down to the `/bins/mirai.arm7` URL and the `ECCHI` busybox probe.

| Source | Events | Nature |
|---|---:|---|
| `136.158.56.92` | 1,442 | This repo's test client, run from a home connection |
| `172.18.0.1` | 121 | Local loopback testing on the VM |
| **Everything else** | **3,714** | **Genuine unsolicited internet traffic** |

The README's safety note promises that generated demo data can never be mistaken
for real data. That holds for `tools/seed_fake_data.py`, which uses reserved
ranges and stamps `geo_source: synthetic`. It does **not** hold for the live
traffic generator, which is a real TCP client from a real address. Every headline
figure below therefore excludes both sources above.

**Fix for future runs:** set `IGNORE_IPS=<your address>` in `.env` — the sensor
already supports an allowlist and will drop those events at admission rather
than recording them.

The production API image deliberately ships without `tests/` or dev

### One failure, found only on real infrastructure

`test_private_ip_has_no_indicator_match` asserted that `192.0.2.99` scores zero
against threat intel, with a comment noting that no indicator files are loaded
in CI. That assumption held in CI and nowhere else: the VM mounts live feeds, and
FireHOL's level-1 list contains the RFC 5737 documentation ranges, so the IP
scored 25.0.

The test was wrong, not the code. It now redirects `INDICATOR_DIR` at an empty
temp directory so it controls its own inputs and asserts the same thing in both
environments. Fixed in `a734ec1`; verified passing locally both with and without
feeds present, and on the VM.

## Network security group review

Effective inbound rules on the VM at the time of this run:

| Priority | Name | Ports | Source | Verdict |
|---:|---|---|---|---|
| 290 | `Allow-Admin-SSH-62222` | 62222 | **Any** | ⚠️ fixed — see Remediation |
| 300 | `SSH` | 22,23,80,21,6379,3306 | Any | correct as bait; 2375 added in Remediation |
| 65000 | `AllowVnetInBound` | Any | VirtualNetwork | Azure default |

### ⚠️ Admin SSH is exposed to the internet

Rule 290 has **Source = Any**. The runbook is explicit that this rule's source
must be a single workstation address, because an admin SSH port open to the
world defeats the entire point of moving it off 22.

This is not theoretical — the exposure is already being probed. `/var/log/auth.log`
shows **12 failed/invalid-user attempts from 8 distinct addresses** against the
real sshd, including:

```
Invalid user cirros from 118.26.111.107 port 54472
Invalid user admin  from 118.26.111.107 port 36696
```

Volume is low because 62222 is off the common scan path, not because the port is
protected. `fail2ban` is running on the jail and currently shows 0 banned, so
nothing has yet crossed its threshold — it is a backstop, not a substitute for
the source restriction.

**Fix — restrict rule 290 to your own address:**

```bash
az network nsg rule update --resource-group <RG> --nsg-name <NSG> \
  --name Allow-Admin-SSH-62222 --source-address-prefixes <YOUR_IP>/32
```

Every honeypot bait port *should* be open to `Any`; that is the design. The
admin plane is the one thing that must not be, and it is the one thing currently
sharing that setting.

## Remediation applied — same day

All three findings were fixed and verified during this run.

### 1. Admin SSH locked down ✅

```
Allow-Admin-SSH-62222  sourceAddressPrefix: "*"  →  "136.158.56.92/32"
```

Verified: admin SSH still reachable from the permitted address after the change.
Because the address is residential and will rotate, expect to re-run this from
Azure Cloud Shell whenever the ISP reassigns it:

```bash
az network nsg rule update --resource-group honeypot-vm_group \
  --nsg-name honeypot-vm-nsg --name Allow-Admin-SSH-62222 \
  --source-address-prefixes <NEW_IP>/32
```

### 2. Docker bait exposed ✅

```
SSH  destinationPortRanges: 22,23,80,21,6379,3306  →  + 2375
```

Verified end-to-end from off-host: `GET /version` returned the emulated daemon
banner, and a host-mount container-create was recorded `critical` and raised
both Docker rules.

```
[medium  ] Docker API enumeration                x1
[critical] Docker host filesystem mount attempt  x1
```

The bait is now live to the internet. Its four rules move from `rule-only` to
observed as soon as real scanners find it — 2375 is heavily swept, so this
should be days, not weeks.

### 3. Test traffic no longer pollutes the dataset ✅

`IGNORE_IPS=136.158.56.92` is set in `.env` and wired into the sensor service.
Verified by probing the bait twice from that address and confirming the event
count did not move (12 → 12). The sensor drops those connections at admission
rather than recording them.

**Note:** this also means running `attacker/run.py` from that address will now
produce no events at all. Unset `IGNORE_IPS` temporarily if you want to exercise
the sensor and see the results.

### Daily digest scheduled ✅

A live digest was delivered to Discord successfully (`exit=0`, 5,283 events),
and a cron entry now sends one every day at 07:00 UTC.

## Remaining decision

**The 1,442 test-client events are still in the production database.** No further
pollution can occur, but the existing rows remain. They are real TCP sessions and
not dishonest to keep — but they are not attacks, and the distinction is far
easier to defend if it lives in the data rather than in a footnote. Pruning them
would leave 3,714 events that are entirely genuine.

Deferred deliberately: with the NSG now correct, it is worth letting clean data
accumulate for a few days first and then deciding whether the older mixed data is
worth keeping at all.
